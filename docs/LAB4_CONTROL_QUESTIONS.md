# Лабораторна робота №4. Відповіді на контрольні запитання

## 1. Web API, MVC та Blazor

ASP.NET Core Web API надає HTTP-інтерфейс для клієнтів і зазвичай повертає JSON. MVC формує HTML на сервері через контролери та представлення Razor. Blazor Web App дає змогу будувати інтерфейс із компонентів Razor із різними режимами інтерактивності. У роботі `MusicContest.REST` обслуговує REST-запити, а `MusicContest.MVC` відображає таблиці пісень і виступів.

## 2. Трирівнева архітектура

Рівень представлення містить контролери й DTO в `MusicContest.REST`. Рівень логіки представлено контрактом `ICrudServiceAsync<T>` і сервісом `RepositoryCrudServiceAsync<T>`. Рівень даних складається з `IRepository<T>`, `EfRepository<T>`, `MusicContestContext` і SQLite. Поділ обмежує залежність HTTP-коду від способу зберігання даних.

## 3. DTO та сутності бази даних

`SongRequest`, `SongResponse`, `PerformanceRequest` і `PerformanceResponse` знаходяться в папці `Models` REST-проєкту. Вони містять лише поля, потрібні для HTTP-взаємодії. Моделі EF Core додатково містять `DatabaseId` і навігаційні властивості. Пряме повернення EF-сутностей могло б розкривати зайві поля та циклічні зв'язки.

## 4. REST та однорідність інтерфейсу

Ресурси названі іменниками у множині: `/api/songs` і `/api/performances`. Ідентифікатор передається в маршруті, спосіб дії визначає HTTP-метод, результат позначається кодом стану. Це забезпечує передбачувану взаємодію клієнта із сервером.

## 5. HTTP-методи CRUD

`POST /api/songs` створює запис; `GET /api/songs/{id}` читає його; `PUT /api/songs/{id}` оновлює; `DELETE /api/songs/{id}` видаляє. Аналогічні маршрути реалізовано для виступів.

## 6. HTTP-коди

`200 OK` означає успішне читання, `201 Created` містить новий ресурс і заголовок Location. `204 No Content` повертається після успішного оновлення або видалення. `400 Bad Request` застосовується для некоректних параметрів і моделей. `404 Not Found` вказує, що запис відсутній. `409 Conflict` використовується при конфлікті створення.

## 7. Асинхронний CRUD

Контракт `ICrudServiceAsync<T>` містить `CreateAsync`, `ReadAsync`, `ReadAllAsync`, `UpdateAsync`, `RemoveAsync` і `SaveAsync`. Реалізація з лабораторної №3 використовує асинхронні операції EF Core. `await` дозволяє не блокувати робочий потік під час асинхронного очікування введення-виведення, проте сам собою не пришвидшує обчислення.

## 8. Dependency Injection

У `Program.cs` реєструються `MusicContestContext`, `IRepository<SongModel>`, `IRepository<PerformanceModel>` та відповідні `ICrudServiceAsync<T>`. Контролери отримують залежності через параметри конструктора. Життєвий цикл scoped дає окремий контекст на HTTP-запит.

## 9. Пагінація

`ReadAllAsync(page, amount)` використовує `Skip` і `Take` після впорядкування записів. Сторінки нумеруються з одиниці. Контролери обмежують розмір сторінки до 100 елементів і повертають `400` для некоректних параметрів. Це зменшує обсяг одного HTTP-відповідного повідомлення.

## 10. Тестування API та PDF

У проєкті є скрипт `scripts/check_lab4_api.py`, який робить фактичні GET, POST, PUT і DELETE запити та перевіряє HTTP-коди. Після успішного запуску результати записуються в `docs/Lab4_http_results.json`, а генератор формує `docs/Lab4_Report.pdf`. Заповнювати звіт неперевіреними відповідями не можна. Також доступна документація Swagger UI.

## 11. Створення MVC-проєкту

Проєкт `MusicContest.MVC` використовує SDK `Microsoft.NET.Sdk.Web`, реєструє MVC у `Program.cs`, містить контролер `HomeController` і Razor-представлення `Views/Home/Index.cshtml`. На відміну від Web API, його основний результат є HTML-сторінкою.

## 12. Повторне використання моделей і контексту

MVC-проєкт посилається на `MusicContest.Infrastructure` і використовує наявний `MusicContestContext`. Контролер читає `Songs` і `Performances` через EF Core та передає їх до Razor. Структура SQLite і моделі не дублюються у вебпроєкті.
